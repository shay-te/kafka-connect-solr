# Feature parity vs kafka-connect-elasticsearch

Deep audit. Every config key, every code class in the ES connector mapped
against the Solr connector. The honest answer is **no, we do not yet
support everything the ES connector does**. Below is exactly what we
match, what is intentionally different, and what is a real gap.

## Behaviour gaps that matter operationally

1. **Async offsets**. ES can ACK Kafka offsets faster than docs are
   indexed by tracking each write's state. We always wait for the bulk
   to flush in `preCommit`. On slow Solr clusters this caps throughput
   at `batch * inFlight / commit_interval`.
2. **External versioning**. ES uses Kafka offset as `_version` so retries
   never overwrite newer data. We rely on the unique-key strategy + at-
   least-once semantics; concurrent writers to the same id can race.
3. **Resource existence check on start**. ES fails fast if the index
   doesn't exist and auto-create is off. We discover at first write,
   which surfaces as a flood of 4xx in the DLQ instead of a clean start-
   up failure.
4. **Per-topic flags**. ES lets ops set `topic.key.ignore=topicA,topicB`.
   We force the same `key.ignore` for every topic the task consumes.
5. **Bulk byte sizing**. ES splits a request when it crosses `bulk.size.bytes`.
   We only cap by record count, which can produce oversized requests on
   wide documents.
6. **HTTP proxy + SSL + Kerberos**. Enterprise networks usually require
   at least one of these and we have none surfaced as connector config.
   SolrJ itself supports SSL and Kerberos but only via JVM system
   properties — not nice for Connect operators.
7. **Connection compression**. ES has it; HTTP/2 helps with framing but
   if Solr is on a WAN, payload gzip would still help.

| Head-to-head benchmark | ❌ | ✅ `SolrVsElasticsearchPerfTest` |

## TL;DR

**No**, we don't match every feature. The ES connector is a 6-year mature
piece of code with enterprise add-ons (Kerberos, SSL, proxy, async
offsets, byte-sized bulks). The Solr connector covers the **core write
path** completely and beats the ES connector on raw throughput, but
the following must land before we can claim full parity:

1. SSL/TLS configuration (`elastic.security.protocol` analogue +
   keystore/truststore keys).
2. HTTP proxy (`proxy.host`, `proxy.port`, `proxy.username`,
   `proxy.password`).
3. Kerberos (`kerberos.user.principal`, `kerberos.keytab.path`).
4. `bulk.size.bytes` byte-size batching.
5. `flush.synchronously=false` async mode + an `OffsetTracker`
   abstraction.
6. `external.version.header` for optimistic concurrency.
7. Per-topic ignore lists (`topic.key.ignore`, `topic.schema.ignore`).
8. Boot-time existence check + auto-create for the target collection.
9. Validator class with proper ConfigDef recommenders.
10. `connection.compression`.

The Solr-specific advantages (HTTP/2, ATOMIC_UPDATE, regex collection
mapping, more id strategies, WKB SMT) are real wins, but they don't
substitute for the gaps above when you're an enterprise customer
moving from the ES connector.
